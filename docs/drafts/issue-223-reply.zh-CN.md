# Issue #223 回复稿（docker logs -f 界面乱码）

## 结论

截图里满屏的 `^[[C` 不是渲染乱码，而是**方向键转义序列的回显**：`^[[C` 就是右方向键（ESC [ C）的「脱字符表示法」。前台跑着 `docker logs --tail 500 -f` 这类不读键盘输入的命令时，按方向键的字节会进入远端终端的行规程（line discipline）；行规程按 ECHOCTL 约定把控制序列以 `^[`、`^[[C` 的形式回显到屏幕上。这与插件无关，iTerm2 / Terminal.app 直连同一台机器跑同样的命令、按同样的键，会出现一模一样的 `^[[C` 刷屏。「时不时出现」是因为只有在前台命令占用期间按键才会出现；命令退出（Ctrl+C）后提示符恢复正常。

我们已核查插件的完整链路（输入队列无重发机制、显示管线逐字节保真、xterm 对跨帧 UTF-8 有状态解码），均不会放大或篡改该现象。

## 建议回复文案（可直接贴）

> 感谢反馈！截图里的 `^[[C` 不是乱码，是方向键的键盘回显：`docker logs -f` 在前台运行时不读取键盘输入，此时按方向键，按键序列（ESC [ C）会被远端 tty 以 `^[[C` 的形式原样回显到屏幕上——这是 Linux 终端的标准行为（ECHOCTL），用 iTerm2/Terminal.app 直连也会出现同样的现象。日志刷屏期间按方向键/其他控制键都会留下这类痕迹，Ctrl+C 退出跟踪后提示符即恢复正常。如果不需要跟踪期间翻页，可以少按方向键；需要检索历史日志的话，建议 `docker logs --tail 500 > /tmp/app.log` 后用 less 打开查看。
>
> 如果您看到的「乱码」不是 `^[[C` 这类字符，而是汉字变成问号/方块，麻烦补充一下远端系统 locale（`locale` 命令输出）与终端字体设置，我们再进一步排查。

## 排查记录（内部）

- 前端显示链路（zmodem/trzsz passthrough → 合帧写节流 → xterm.write 原始字节）逐字节保真；xterm.js 对跨帧分割的 UTF-8 多字节字符有状态化解码，不会产生间歇性替换符。
- 输入队列（lib/terminalInputQueue.ts）超时仅报错并触发重连守望，**不重发字节**，不存在按键放大。
- sidecar PTY 输出转发为二进制帧透传，无编码改写。
